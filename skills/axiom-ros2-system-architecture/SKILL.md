## 7. ROS2 system architecture, DDS, build, and deployment (production-grade)

### 7.1 DDS configuration
Choose DDS implementation per use case (FastDDS default for multi-machine; CycloneDDS for reliability). Tune via XML config (CycloneDDS/FastDDS). Key settings: discovery (SPDP), unicast peers for containers, shared memory transport, ROS_DOMAIN_ID for isolation, ROS_LOCALHOST_ONLY for single-machine dev. Debug discovery with `ros2 doctor`, `ros2 daemon`, participant list.

### 7.2 Build system (colcon)
Workspace: src/ -> build/ -> install/ -> log/. Use `--symlink-install` for Python iteration. Build specific packages for speed. Run rosdep for dependencies. Use `--cmake-args -DCMAKE_BUILD_TYPE=Release`. Troubleshoot: source underlay before overlay; check package.xml exec_depend for custom msgs; clean build on stale artifacts. Never source setup.bash from build/.

### 7.3 Package structure
ament_cmake for C++ (CMakeLists with find_package, ament_target_dependencies, install rules). ament_python for pure Python (setup.py/setup.cfg with entry_points). Declare deps in package.xml (build_depend, exec_depend, test_depend). Custom msg/srv/action in dedicated interface packages.

### 7.4 Debugging toolkit
Topic inspection (ros2 topic list/echo/hz/bw), node inspection (ros2 node list/info), parameter management (ros2 param), lifecycle management (ros2 lifecycle), service calls (ros2 service call), action monitoring (ros2 action), bag recording (ros2 bag record/play), DDS debugging (rmw, participant info).

### 7.5 Containerized deployment (Docker + ROS2)
- Multi-stage Dockerfiles: dependency base -> dev -> build -> runtime (minimal). Copy package.xml first for cache.
- One container per subsystem (not monolithic). Use compose with health checks and profiles.
- DDS across containers: host networking (simplest) or bridge with CycloneDDS unicast peers. Configure ROS_DOMAIN_ID per robot.
- GPU passthrough via NVIDIA Container Toolkit for perception. Display forwarding (X11/Wayland/Xvfb).
- Volume mounts: mount source only, named volumes for build artifacts. ccache for faster rebuilds.
- USB device passthrough via --device and udev rules. Devcontainers for consistent dev env.
- CI/CD: GitHub Actions with layer caching and build matrix across ROS distros.
- Anti-patterns: monolithic container, bridge without DDS config, build tools in runtime, mounting entire workspace, running as root, ignoring cache order, hardcoded ROS_DOMAIN_ID, forgetting setup.bash sourcing.

### 7.6 Web integration (rosbridge / custom bridge)
- rosbridge_suite for simple topic/service access from JS (roslibjs). Limitations: performance, no auth by default.
- Custom FastAPI bridge: ROS2 node with async executor + FastAPI app; WebSocket streaming; REST wrapping services; JWT auth; CORS allowlist; Nginx reverse proxy with TLS.
- Flask alternative for simpler cases (threaded executor).
- Video streaming: MJPEG, WebRTC (webrtc_ros), compressed topic streaming as binary WebSocket.
- Bidirectional: command ack pattern with progress updates; rate limiting (token bucket); client backpressure; adaptive quality.
- Anti-patterns: blocking executor from HTTP handlers, streaming raw images, no rate limiting, rosbridge without auth, sync service calls in async handlers, GIL contention, no connection lifecycle, exposing all topics.

## 7. ROS2 node design and QoS (production-grade)

### 7.1 Node design patterns
- Use lifecycle (managed) nodes for components that need configure/activate/deactivate/cleanup/shutdown.
- Separate concerns: one node per responsibility (sensor, processing, control, I/O).
- Use components (composable nodes) for zero-copy in-process communication and flexible deployment.
- Use actions (not services) for long-running tasks with feedback and cancellation.

### 7.2 Lifecycle nodes
States: Unconfigured -> Inactive -> Active -> Finalized. Transitions: configure, activate, deactivate, cleanup, shutdown. Implement on_configure, on_activate, on_deactivate, on_cleanup, on_shutdown. Ensure clean resource acquisition/release per state.

### 7.3 QoS (the #1 source of ROS2 bugs)
Match QoS between publisher and subscriber or messages are silently dropped.
- **Sensor data** (cameras, lidars): best-effort, keep-last, small depth (tolerate drops, want latest).
- **Commands** (velocity, joint): reliable, keep-last, small depth (never miss).
- **Map/static data**: reliable, transient-local (late joiners get it).
- **Default/parameter**: reliable, keep-last with some history.
Debug: check QoS info (`ros2 topic info -v`), look for "Reliability"/"Durability" fields, check incompatible QoS events. If 0 subscribers despite nodes running -> QoS mismatch.

### 7.4 Launch files (Python)
Use Python launch files for flexibility. Layer: hardware launch -> driver launch -> perception launch -> application launch -> top-level bringup. Conditional loading for sim vs real and robot variants. Use launch arguments for configuration.

### 7.5 Components (composable nodes)
Register components with `rclcpp_components_register_node`. Load via `ComposableNodeContainer` for in-process zero-copy. Enables flexible deployment (single process or multi-process).

### 7.6 Actions
Use for long-running tasks with goal/result/feedback. Implement action server with goal acceptance, execution, cancellation, result. Use action client with feedback callbacks.

### 7.7 Production deployment checklist
- [ ] Lifecycle nodes used where state management needed
- [ ] QoS matched between publishers and subscribers
- [ ] Components used for performance-critical paths
- [ ] Actions used for long-running tasks (not services)
- [ ] Launch files layered and parameterized
- [ ] No hardcoded topics/params (use launch args + config)
- [ ] Graceful shutdown handlers present
- [ ] Health checks / watchdogs in place
- [ ] Logging structured and rate-limited
- [ ] Tested with launch_testing
